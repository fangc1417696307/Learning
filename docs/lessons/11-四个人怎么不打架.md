# 第 11 课：四个人怎么不打架

> **日期**：2026-10-23
> **前置**：第 2 课（Git 基础）、第 10 课（已经推到 GitHub）
> **目标**：让 4 个人能同时改代码而不互相破坏

---

## 一、现状：一条独木桥

你现在是这样：

```bash
git add .
git commit -m "..."
git push
```

提交直接进 `main`，`main` 直接同步到 GitHub。

**一个人这么干，完全没问题。** 两个人就不行了：

```
你：  改 routers/profile.py 第 30 行 → commit → push  ✅
队友：改 routers/profile.py 第 30 行 → commit → push  ❌ 被拒
```

**队友的 push 会失败**，因为远端已经有他不知道的提交。他必须先 `git pull`——**而如果你们改的是同一行，这一刻冲突就爆发了**。

### 更糟的情况：代码能推上去，但已经坏了

```
你：  改了 schemas.py 的字段名 → push
队友：不知道，还在用老字段名 → 他的功能悄悄坏了 → 两天后才发现
```

**没有 review，这种问题只能靠"谁先撞墙"发现。**

## 二、分支：另一条提交线

**分支就是从一个提交点，再拉出一条平行的线。**

```
              ●───●───●   feature/login      ← 你在这条线上改
             /
●───●───●───●              main             ← 主干一直是好的
```

两条线互不影响。你那边的代码写崩了，`main` 毫发无伤。

**改好了** → 合并（merge）回 `main`。
**改废了** → 扔掉这条分支，主干净利落。

> **分支的核心价值：把"试验"和"确定能用"隔开。**
> `main` 上永远是"能跑的版本"，这是团队协作的第一条铁律。

## 三、一天的完整流程

```bash
# ① 每天开始前，先同步主干（防止你的起点太旧）
git switch main
git pull

# ② 开一条自己的分支，名字说明干什么
git switch -c feature/profile-api

# ③ 干活，小步提交
git add backend/routers/profile.py
git commit -m "feat: 新增画像查询接口"

# ④ 推到远端（-u 只在第一次需要）
git push -u origin feature/profile-api

# ⑤ 去 GitHub 开 PR

# ⑥ 队友 review，你根据意见再提交、再 push（PR 自动更新）

# ⑦ 合并，删掉分支

# ⑧ 回到主干，拉最新
git switch main
git pull
```

### 命令速查

| 命令 | 干什么 |
|---|---|
| `git switch -c <名字>` | 新建并切换分支 |
| `git switch <名字>` | 切换分支 |
| `git branch` | 列出本地分支（`*` 是当前） |
| `git branch -d <名字>` | 删除已合并的本地分支 |
| `git push -u origin <名字>` | 首次推送并记住远端 |
| `git merge <名字>` | 把某条分支合并进当前分支 |

> ⚠️ **切换分支前先 commit 或 stash。** 有未提交的改动时切分支，可能把改动带过去，很乱。

## 四、PR：合并之前，先有人看一眼

**PR（Pull Request）不是 Git 的命令，是 GitHub 的功能。**

它的流程是：

```
你的分支  ──────────►  main
          PR（申请合并）
          ↑
     GitHub 把两边差异列出来
     队友逐行看、留评论
     你说"有道理，改了" → 再 push
```

### 为什么不能直接合并

| 没有 PR | 有 PR |
|---|---|
| 只有你知道改了什么 | 改动**可见**，别人能看懂 |
| 错误进了主干才发现 | 错误**在合并前**被发现 |
| 历史里只有"111" | 每个 PR 是一份**变更说明** |

> **PR 的真正价值不是"合并"这个动作，是"合并之前必须有人看"这个约束。**

### 一条实际的 review 意见长什么样

```diff
- def get_profile(student_id: int):
+ def get_profile(student_id: int, conn: ConnDep):
```

> 评论：「这里没有限制只能查自己的数据，改 id 能读别人。」

**这就是第 18 课要修的那个漏洞**——一个人写代码很难看见自己的盲区，**别人一眼就看出来**。

## 五、冲突：一定会遇到，而且不可怕

### 5.1 冲突是怎么来的

Git 合并时，如果**同一个文件的同一块内容**，两边改得不一样，它就不知道听谁的：

```
你的分支：   conn = db.get_conn()
main：     conn = get_conn()          ← 同一行，两个版本
```

**它不会瞎猜，也不会覆盖，而是停下来问你。**

> **冲突不是错误，是"需要你决策"的信号。**

### 5.2 冲突长什么样

Git 会在文件里插标记：

```python
<<<<<<< HEAD
conn = db.get_conn()          # 当前分支（你要合入的那边）
=======
conn = get_conn()             # 要合进来的那边
>>>>>>> feature/xxx
```

**你要做的就是：删掉标记，留下正确的代码。**

### 5.3 动手：自己制造一次冲突

**一个人就能练。** 在项目根目录（`Learning/`）执行：

```bash
# ① 确认在干净的 main 上
git switch main
git status

# ② 开一条练习分支
git switch -c experiment/conflict

# ③ 改 README 或者随便一个文件的一行（新建 docs/test.md 也行，先提交它）
echo "第一行：来自分支" > conflict_test.md
git add conflict_test.md
git commit -m "test: 分支版本"

# ④ 切回 main，改同一个文件的同一行
git switch main
echo "第一行：来自主干" > conflict_test.md
git add conflict_test.md
git commit -m "test: 主干版本"

# ⑤ 合并，看冲突
git merge experiment/conflict
```

**你会看到**：

```
CONFLICT (add/add): Merge conflict in conflict_test.md
Automatic merge failed; fix conflicts and then commit the result.
```

**打开 `conflict_test.md`**，会看到 `<<<<<<<` 那一堆。

**解决它**（留一行，删标记），然后：

```bash
git add conflict_test.md
git commit -m "chore: 解决冲突"
git branch -d experiment/conflict
```

**做完把 `conflict_test.md` 删掉，再提交一次。**

> **这一步一定要亲手做。** 没解过冲突的人，第一次遇到会慌；解过一次，就是"哦，就这"。

### 5.4 减少冲突的四个习惯

| 习惯 | 作用 |
|---|---|
| **分支活得短** | 一天内合并掉，别攒一周 |
| **每次 pull 后再开工** | 起点别太旧 |
| **一个分支只干一件事** | 别在"加登录"的分支里顺手改格式 |
| **别大范围重排文件** | 重命名、大改格式单独一次做 |

## 六、GitHub 上的设置（**今天就去改**）

在仓库页面：**Settings → Branches → Add branch protection rule**

| 设置 | 建议 | 为什么 |
|---|---|---|
| Branch name pattern | `main` | 保护主干 |
| Require a pull request before merging | ✅ | 禁止直接推 |
| Require approvals | ✅ 1 | 至少要一个人看过 |
| Do not allow bypassing | ✅ | 包括你自己 |

> **另外两件事**：
> 1. **仓库改 private。** 课程项目没必要公开，而且后面会有 API key 的配置文件
> 2. **组员用 `git clone` 拿代码**，不要复制文件夹——复制过去的没有 `.git`，是另一个独立仓库

## 七、给组员的"一页纸"

你可以在群里直接发这段：

```
【Git 协作规则 v1】

1. 不要直接推 main。所有改动走分支 + PR。
2. 分支命名：
   feature/xxx   新功能
   fix/xxx       修 bug
   docs/xxx      文档
3. 每天开工前：
   git switch main && git pull
4. 干活流程：
   git switch -c feature/你要做的事
   （改代码）
   git add <你改的文件>        ← 别用 git add .（会带进不该提交的东西）
   git commit -m "feat: 简短说明"
   git push -u origin feature/你要做的事
   → 去 GitHub 开 PR，描述一下改了什么、为什么改
5. 提交信息格式：feat: / fix: / docs: / chore: / refactor: + 空格 + 说明
6. 不会的地方先问，别硬推。
```

## 九、几个会遇到的坑

### 9.1 `git push` 报 rejected

```
! [rejected] main -> main (fetch first)
```

**意思**：远端有你没有的提交。先 `git pull`。

> **但更该反思的是**：你为什么直接推 `main` 了？

### 9.2 `fatal: not possible to fast-forward`

两边的历史已经分叉了。`git pull` 默认会尝试 merge；如果冲突，按第 5 节处理。

### 9.3 别乱用 `git push -f`

**强制推送会覆盖远端历史**，队友的提交可能直接消失。

> **`-f` 是团队协作里的禁区。** 除非你完全确定自己在做什么，而且提前通知了所有人。

### 9.4 提交里混进了不该提交的东西

```bash
git status             # 看清单
git restore --staged <文件>   # 从暂存区拿出来
```

**这就是为什么第 7 节说别用 `git add .`**——它会把你没注意到的所有文件都加进去。

### 9.5 `.git` 文件夹是仓库本身

**复制文件夹给组员 ≠ 分享仓库。** 复制会带走 `.git`，但那是一个**独立的历史**，跟你的毫无关系。

**分享仓库只有一种方式：push 到远端，别人 clone。**

## 十一、备忘

- `git switch -c <名字>` 开分支 / `git switch <名字>` 切换 / `git branch` 查看
- `git push -u origin <名字>` 首次推送
- 每天开工：`git switch main` → `git pull`
- 冲突标记：`<<<<<<<`（当前） / `=======`（分隔） / `>>>>>>>`（要合进来的）
- 解决冲突：**删标记、留正确代码、`git add`、`git commit`**
- **不允许直接推 `main`**；`git push -f` 是禁区
