# 第 12 课：密钥不能写在代码里

> **日期**：2026-10-23
> **前置**：第 11 课（已经会用分支和 PR）
> **目标**：把配置和代码分开，学会安全管理密钥

---

## 一、为什么现在讲这个

下一课开始要接大模型了。你需要一样东西：**API key**（一串 `sk-` 开头的字符）。

**它等于钱。** 谁拿到它，就能用你的账号额度调模型——**费用算在你头上**。

而这个 key 的自然写法是：

```python
API_KEY = "sk-abc123..."       # ← 就写在这儿，多方便
```

**这一课就是讲清楚：为什么绝对不能这么写。**

---

## 二、写进代码会发生什么

### 2.1 它会进 Git 历史——而且删不掉

你可能会想：那我写完，等提交前删掉不就行了？

看看会发生什么：

```bash
# 第一次提交，密钥在里面
git commit -m "feat: 接入大模型"

# 发现不对，删掉密钥，再提交一次
git commit -m "fix: 移除密钥"
```

**现在 `git log` 里第一次提交还在。** 任何人执行：

```bash
git log -p | grep -i "sk-"
```

**就能把密钥翻出来。**

> **Git 的设计是"记录一切、永不遗忘"。** 这对代码是好事，对密钥是灾难。
>
> **"提交过一次"就等于"永久公开过"**——尤其在你已经推到 GitHub 之后。

### 2.2 删掉整个文件也没用

```bash
git rm config.py
git commit -m "chore: 删除配置文件"
```

**历史里的那个版本依然存在。** 你可以 `git checkout <老提交>` 把它原样拿回来。

想把历史真的洗干净，得用 `git filter-repo` 或 BFG 重写全部提交——**所有 commit hash 都会变，队友的本地仓库全部作废**。这是个大手术，而且**做完也不能保证没人已经拿到过**。

### 2.3 公开仓库的自动爬虫

GitHub 上有大量机器人**24 小时扫描新提交**里像密钥的字符串。有统计说公开仓库泄露的 key **平均几分钟内就会被尝试使用**。

**不是"有没有人看"，是"什么时候被用掉"。**

---

## 三、泄露之后的第一件事：吊销，不是删除

**这个顺序很重要，记牢：**

| 顺序 | 动作 | 说明 |
|---|---|---|
| **1** | **立刻去平台后台吊销 / 轮换这个 key** | 让它当场失效。**这一步和清理代码无关** |
| 2 | 检查用量和账单 | 看有没有被滥用 |
| 3 | 再清理代码和 Git 历史 | 防止以后再被翻出来 |

**很多人第一反应是"赶紧删代码"，但那时候 key 已经泄露了。** 代码删得再干净，key 照样能用。

> **"泄露"是既成事实，处置方式是让泄露的东西失效，而不是让证据消失。**

---

## 四、正确做法：配置与代码分离

### 4.1 核心原则

> **代码描述"程序怎么运行"，配置描述"这次在什么环境里运行"。**
>
> 两者变化频率完全不同——**代码写完基本不动，配置换个部署环境就得改**。

这条原则有个正式名字：**12-Factor App 的 Config 原则**——"配置存在环境变量里，不写在代码里"。面试问到部署，多半会碰到这个词。

### 4.2 怎么做：`.env` 文件 + 环境变量

在 `backend/` 下建一个 **`.env`** 文件（**注意文件名前面有个点**）：

```
LLM_API_KEY=sk-你的真实密钥
DB_PATH=student.db
```

然后在 `.gitignore` 里加一行：

```
.env
```

**`.env` 只活在你自己的电脑上，永远不进仓库。**

### 4.3 同时提交一份 `.env.example`

新建 `backend/.env.example`，内容一样但**值全是占位**：

```
LLM_API_KEY=在这里填你自己的密钥
DB_PATH=student.db
```

**这个文件要提交。**

> **作用**：新来的组员 clone 下来，一看就知道"需要配哪些变量、格式是什么"。
> **没有它，新人只能靠猜或者问你**——而你可能早就忘了。

### 4.4 一套文件的分工

| 文件 | 进 Git 吗 | 里面是什么 |
|---|---|---|
| `.env` | ❌ | 真实密钥 |
| `.env.example` | ✅ | 变量名 + 占位值 |
| `config.py` | ✅ | 读取和校验配置的代码 |

## 五、代码里怎么读

### 5.1 最朴素的做法：`os.environ`

```python
import os

api_key = os.environ.get("LLM_API_KEY", "")
```

**能跑，但有问题**：

- **环境变量全是字符串**。`PORT=8001` 读出来是 `"8001"`，不是 `8001`
- 缺了变量只会得到 `None` 或空串，**报错要等到真正用的时候**
- 分散在各个文件里，改一次找半天

### 5.2 推荐：`pydantic-settings`

你的项目已经用了 Pydantic（第 3 课），这个库是它的配置版：

```bash
pip install pydantic-settings
```

新建 `backend/config.py`：

```python
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",              # 自动读这个文件
        env_file_encoding="utf-8",    # 中文值不乱码
        extra="ignore",               # .env 里多出来的变量不报错
    )

    db_path: str = "student.db"
    llm_api_key: str = ""
    llm_base_url: str = "https://api.example.com/v1"
    llm_model: str = "some-model"


settings = Settings()
```

**它的三个好处，正好对应刚才的三个问题**：

| 问题 | `Settings` 怎么解决 |
|---|---|
| 全是字符串 | 写了 `age: int` 就自动转成 `int`，转不了直接报错 |
| 缺变量晚报错 | **启动时**就报，缺什么一目了然 |
| 分散 | 所有配置集中在一个类里 |

**名字怎么对应**：类里的 `llm_api_key` ←→ 环境变量 `LLM_API_KEY`（大小写不敏感）。

**`db_path: str = "student.db"` 里的 `= "student.db"` 是默认值**——和 Pydantic 模型的默认值是一个机制（第 3 课）。

### 5.3 改 `db.py`

```python
import sqlite3

from config import settings

DB_PATH = settings.db_path


def get_conn():
    return sqlite3.connect(DB_PATH)
```

**改完之后，数据库路径不再写死在代码里**——换台机器、换个部署方式，改 `.env` 就行。

## 七、验证（**这一节不能省**）

第 2 课的教训：**"看起来对了"和"真的对了"是两件事。**

```bash
git check-ignore -v backend/.env        # 有输出 = 被忽略
git status                              # .env 不应该出现在清单里
git status --short | grep env           # 应该只看到 .env.example
```

**三条都要跑。** 尤其第一条——如果 `.gitignore` 又因为缩进出问题（第 2 课踩过），前两条可能"看起来正常"但你并不知道为什么。

### 如果 `.env` 已经被提交过了

```bash
git rm --cached backend/.env      # 从版本控制里移除，但文件留在本地
git commit -m "chore: 移除已提交的 .env"
```

> ⚠️ **这只能防以后**。如果它已经推到 GitHub 了，**必须去吊销密钥**（第三节）。

## 八、坑

### 8.1 在日志里打印配置

```python
print(settings)                  # ❌ 会把密钥原样打出来
logger.info(f"配置: {settings}")  # ❌ 日志会被收集、上传、长期保存
```

**日志比代码更容易泄露**——代码在仓库里权限受限，日志可能发到第三方平台、可能被截图、可能留好几年。

> 要打印配置，**手动挑出安全的字段**：路径、模型名、超时时间可以，密钥不行。
>
> **第 33 课「出事了怎么查」会讲这个。**

### 8.2 把 `.env` 发给组员

**不要。** 每个人用自己的 key，或者由组长统一管控。

**通过微信/QQ 传密钥，和贴在 GitHub 上区别不大。**

### 8.3 以为 `.env` 在线上也有用

`.env` 是**本地开发**的便利。真正部署时，配置来自**平台提供的环境变量面板**（Docker 的 `-e`、云平台的设置页）。

**代码不用改**——这正是"配置与代码分离"的价值：**换环境只换配置，代码一个字不动。**

### 8.4 `.env` 里的值带引号或空格

```
LLM_API_KEY="sk-xxx"      # 引号会被当成值的一部分（取决于解析器）
LLM_API_KEY = sk-xxx      # 等号两边有空格，可能出问题
```

**老老实实写 `KEY=值`，不加引号、不加空格。**

## 十一、总结

这一课只有一句话，但值的分量很大：

> **代码里不能有任何"只属于这台机器"的东西。**

具体到三层：

| 层面 | 结论 |
|---|---|
| **安全** | 密钥泄露不可逆；第一动作是**吊销**，不是删文件 |
| **工程** | 配置集中到一个 `Settings`，启动时校验，代码里只引用 `settings.xxx` |
| **协作** | `.env` 本地私有，`.env.example` 提交，新人照抄就能跑 |

再抽一层，其实是同一个原则贯穿始终：

> **"什么东西该由谁决定"要有明确分工。**
> 数据库路径、密钥、端口 —— 由**环境**决定（配置）。
> 表结构、校验规则、调用流程 —— 由**代码**决定。
>
> 混在一起，换环境就要改代码；分开，换环境只改配置。

这条原则会一直用到后面：第 17 课的认证（签名密钥）、第 32 课的测试（测试库路径）、第 34 课的容器化（环境变量注入），全都是它的延伸。

## 十二、练习答案

<details>
<summary>点开看答案（先自己做！）</summary>

**1.** 三条命令应该分别是：

- `git check-ignore -v backend/.env` → 输出一行类似 `.gitignore:6:.env	backend/.env`（**有输出才算生效**）
- `git status` → 清单里没有 `.env`
- `git status --short | grep env` → 只出现 `.env.example`

**2.** 改 `DB_PATH` 后重启，`backend/` 下会出现一个新的 `demo.db`。**注意**：旧数据不会跟过去，新库里是空表（`init_db()` 会建表）。

**3.** **能启动。** 因为 `Settings` 里每个字段都写了默认值，读不到 `.env` 就用默认值。这既是好事（不配也能跑）也是坏事（**配错了也照样跑**）——所以第 17 题说"存在但是空"比"不存在"更危险。

**4.** 都是**空字符串 `""`**。区别在于：**没写这一行**时你可以给一个明确的默认值来区分"没配"；**写了但是空**则会覆盖掉默认值。所以关键配置（比如密钥）应该在启动时**主动检查非空**，发现是空就直接报错退出。

**5.** `.env.example` 是"说明书"，说明有哪些变量、格式是什么；`.env` 是"真实密钥"，属于这台机器。

只提交前者，新人照样**跑不起来**——他必须自己建 `.env`、填自己的值。**但至少他知道要填什么**。没有 `.env.example`，他只能猜或者问你。

**6.** 顺序：

1. **不要直接用。** 这个 key 已经在群里传过了，视为已泄露。
2. **让同事立刻去平台吊销 / 轮换这个 key**（如果这不是他自己的账号，走负责人）。
3. 提醒他：以后用 `.env`，不要通过聊天工具传密钥；团队统一的 key 由负责人单人保管。

> 注意第一件事是**吊销**，不是"先删聊天记录"。

**7.** `settings = Settings()` 在**模块被 import 时**执行一次——也就是服务启动、第一次 `import config` 的时候。

**运行中改 `.env` 不会生效**，因为值已经读进内存了。要生效必须**重启服务**。

> 这是"配置是启动时快照"的基本认知。第 20 课做后台任务时会再遇到类似的"什么时候读"的问题。

**8.** UTF-16 的文件里每个字符都夹着 `0x00` 字节。`pydantic-settings`（底层用 Python 的文本读取）按 UTF-8 解码会失败，要么报 `UnicodeDecodeError`，要么读出乱码——**配置项全部读不到，于是全部走默认值**。

`env_file_encoding="utf-8"` 就是显式指定"这个文件按 UTF-8 读"。**它不会自动猜编码**——所以文件本身必须是 UTF-8。

这和第 11 课那个"UTF-16 让 Git 认成二进制"是同一个根问题：**编码不统一**。

## 十三、大练习参考答案

<details>
<summary>点开看你该找到的问题</summary>

**问题清单（7 个）**

| # | 位置 | 问题 | 后果 |
|---|---|---|---|
| 1 | `.gitignore` | **缺少 `.env`** | 密钥文件会被提交，等于公开 |
| 2 | `config.py` | **密钥硬编码** `sk-live-...` | 提交后永久留在历史里 |
| 3 | `config.py` | **用 `BaseModel` 而不是 `BaseSettings`** | **根本不读环境变量**，`.env` 形同虚设——最隐蔽的一个 |
| 4 | `config.py` | `show()` **打印整个配置对象** | 密钥进日志 |
| 5 | `db.py` | 仍然硬编码 `DB_PATH = "student.db"` | 有**两个配置来源**，改 `.env` 不生效 |
| 6 | 整个项目 | **没有 `.env` / `.env.example`** | 别人不知道要配什么；迁移时没有模板 |
| 7 | `config.py` | `import os` **没用到** | Ruff 会报 F401（小事，但 review 时要提） |

**第 3 个是最容易被忽略的**：代码"看起来完全正确"——有类、有字段、有默认值——但 `BaseModel` 只做数据校验，**不读环境变量**。这是典型的"AI 给了个能跑但不干活的版本"。

**修好后的样子**

`.gitignore` 追加：

```
.env
```

`config.py`：

```python
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        extra="ignore",
    )

    db_path: str = "student.db"
    llm_api_key: str = ""
    port: int = 8001


settings = Settings()
```

`db.py`：

```python
import sqlite3

from config import settings


def get_conn():
    return sqlite3.connect(settings.db_path)
```

`.env.example`：

```
LLM_API_KEY=在这里填你自己的密钥
DB_PATH=student.db
```

**"能看出配置生效但不能泄露密钥"** 的写法：

```python
print(f"[config] db_path={settings.db_path} model={settings.llm_model} key={'已配置' if settings.llm_api_key else '未配置'}")
```

——**只说"有没有"，不说"是什么"。**
