# 第 13 课：等的时候别干等着 —— 同步与异步

> **日期**：2026-10-27
> **前置**：第 12 课（配置已经抽出来）
> **目标**：理解同步/异步的本质区别，知道 FastAPI 里 `def` 和 `async def` 该选哪个

## 一、下一课要面对的问题

下一课开始调大模型。一次调用的过程是：

```
发请求  →  等 3～10 秒  →  拿到回答
```

**在这 5 秒里，你的服务在干什么？**

看现在的接口——它什么也干不了，就在那儿等。一个人用没问题，20 个人同时用，最坏情况要排队 100 秒。

**这一课要解决的就是这个"等着"的问题。**

---

## 二、先分清两种"忙"

程序的时间花在两类事情上，区别非常关键：

| 类型 | 在干什么 | 例子 | CPU 在干嘛 |
|---|---|---|---|
| **I/O 等待** | 等别人 | 等网络、等磁盘、等数据库 | **闲着** |
| **CPU 计算** | 等自己 | 循环、加密、图像处理 | 忙着算 |

**大模型调用几乎全是"等别人"**——你发出去一个请求，然后几秒钟里 CPU 一点事都没有。

> **这就是异步的全部出发点：既然 CPU 在闲着，为什么不拿它去干别的？**

---

## 三、一个比喻：服务员

**同步**：一个服务员站到一桌旁边，等客人看完菜单、商量好、点完——**期间其他桌没人管**。

**异步**：服务员把菜单放桌上就走，去服务下一桌；谁想好了就招呼一声，他再回来。

**服务员的数量没变**，但因为他不再"站着干等"，同样的时间能应付多得多的桌子。

> **异步不是让单个任务变快，是让"等待的时间"不浪费。**

## 四、Python 的 `async` / `await`

```python
import asyncio


async def make_tea(name):
    print(f"{name} 开始泡茶")
    await asyncio.sleep(3)        # ← 等 3 秒，但把控制权交出去
    print(f"{name} 茶好了")


async def main():
    await asyncio.gather(
        make_tea("A"),
        make_tea("B"),
        make_tea("C"),
    )


asyncio.run(main())
```

**跑一下，你会看到三句话几乎同时打印出来，总耗时约 3 秒，不是 9 秒。**

### 三个关键字

| 写法 | 意思 |
|---|---|
| `async def` | 定义一个**协程函数** |
| `await` | "这里要等，先把控制权让出去" |
| `asyncio.gather(...)` | 同时启动多个协程，等它们全部完成 |

### 一个容易懵的细节

```python
c = make_tea("A")     # 调用 async 函数，什么都不会发生！
print(type(c))        # <class 'coroutine'>  ← 只是拿到一个"待执行的对象"
```

**`async def` 函数被调用时不会执行**，必须被 `await` 或被 `asyncio.run` / `gather` 驱动，才会真正跑。

> 和第 10 课的 `yield` 有点像：**调用 ≠ 执行**。这又是"对象"那一课的延伸。

## 五、FastAPI 里的 `def` 和 `async def`（**这一节最重要**）

这两者**跑在不同的地方**，这是全部区别的来源：

| 写法 | 谁来执行 | 适合放什么 |
|---|---|---|
| `def xxx()` | **线程池**（默认 40 个线程） | 同步阻塞库：`sqlite3`、`requests`、`time.sleep` |
| `async def xxx()` | **事件循环**（单线程） | 真正的异步库：`httpx.AsyncClient`、`asyncio.sleep` |

### 5.1 `def` 接口：并发靠"多开线程"

40 个线程 = 最多同时处理 40 个请求。第 41 个要等前面的腾出位置。

**你的项目现在就是这样**，而且**这是对的**——因为 `sqlite3` 是同步阻塞库。

### 5.2 `async def` 接口：并发靠"不停切换"

只有一个线程，但它在一堆任务之间快速切换，**谁在等就切走**。

所以 1000 个"在等网络"的请求，一个线程就能扛。

### 5.3 ⚠️ 致命错误：在 `async def` 里调阻塞函数

```python
import time
from fastapi import FastAPI

app = FastAPI()


@app.get("/bad")
async def bad():
    time.sleep(3)          # ❌ 整个服务冻住 3 秒
    return {"ok": True}
```

**为什么这么严重**：`async def` 跑在**唯一的事件循环线程**上。`time.sleep` 会让这个线程睡死 3 秒——**期间所有请求（包括别的接口）全部卡住**。

对比：

```python
@app.get("/fine")
def fine():
    time.sleep(3)          # ✅ 只占用线程池里的一个线程
    return {"ok": True}
```

> **同一个 `time.sleep`，写在 `def` 里是"占用一个工位"，写在 `async def` 里是"全店停摆"。**

### 5.4 那张"能不能用"的表

| 你想做的事 | 在 `async def` 里能用吗 |
|---|---|
| `asyncio.sleep()` | ✅ |
| `httpx.AsyncClient` | ✅ |
| `httpx.Client` / `requests.get` | ❌ 阻塞 |
| `time.sleep()` | ❌ 阻塞 |
| `sqlite3` 的各种操作 | ❌ 阻塞（磁盘 IO） |
| 大量纯计算（`for` 循环几百万次） | ⚠️ 会占满事件循环，该扔线程池 |

## 六、什么时候**不需要**异步

**异步不是"更高级"，是"针对一类问题的工具"。**

| 场景 | 要不要异步 |
|---|---|
| 调大模型（一次几秒，同时很多人用） | ✅ **强烈需要** |
| 读写 SQLite | ❌ 保持 `def`，别硬上 |
| 纯计算（图像处理、复杂算法） | ❌ 异步毫无帮助，CPU 本来就忙 |
| 一个人用的内部工具 | ❌ 没必要 |

> **原则：只有"在等别人"才需要异步。** 在等自己（算）的时候，异步只会增加复杂度。

## 七、动手实验：让差别看得见

### 7.1 加三个临时接口

在 `backend/main.py` 里加上（**实验完删掉**）：

```python
import asyncio
import time


@app.get("/slow-sync")
def slow_sync():
    time.sleep(3)                    # def + 阻塞：占一个线程
    return {"mode": "sync"}


@app.get("/slow-async")
async def slow_async():
    await asyncio.sleep(3)           # async + 异步等待：让出事件循环
    return {"mode": "async"}


@app.get("/slow-block")
async def slow_block():
    time.sleep(3)                    # async + 阻塞：全店停摆
    return {"mode": "block"}
```

### 7.2 并发压测脚本

新建 `backend/exp_concurrency.py`（临时文件）：

```python
import time
import urllib.request
from concurrent.futures import ThreadPoolExecutor


def bench(url, n):
    def hit(_):
        with urllib.request.urlopen(url, timeout=300) as r:
            return r.status

    start = time.perf_counter()
    with ThreadPoolExecutor(max_workers=n) as ex:
        list(ex.map(hit, range(n)))
    elapsed = time.perf_counter() - start
    print(f"{url}  {n} 个并发请求  耗时 {elapsed:.1f} 秒")


bench("http://127.0.0.1:8001/slow-sync", 50)
bench("http://127.0.0.1:8001/slow-async", 50)
bench("http://127.0.0.1:8001/slow-block", 5)      # 别用 50，会等很久
```

**先启动服务，再跑脚本。**

### 7.3 预期结果

| 接口 | 预计耗时 | 为什么 |
|---|---|---|
| `/slow-sync` × 50 | **≈ 6 秒** | 线程池 40 个：第一批 40 个跑 3 秒，剩下 10 个再跑 3 秒 |
| `/slow-async` × 50 | **≈ 3 秒** | 50 个任务同时在"等"，互相不挡 |
| `/slow-block` × 5 | **≈ 15 秒** | 每个都要独占事件循环 3 秒，只能排队 |

**`/slow-block` 那三行是这一课的核心。** 5 个请求 = 15 秒，说明它们**完全没并发**——因为 `time.sleep` 把唯一的事件循环线程堵死了。

> 把 `/slow-block` 改成 50 个请求会怎样？**150 秒。** 这就是"线上服务忽然全体卡死"的样子。

## 八、坑

### 8.1 忘记 `await`

```python
@app.get("/x")
async def x():
    result = make_tea("A")     # ❌ 没有 await
    return result              # 返回的是一个 coroutine 对象
```

**不会报语法错误**，但你会得到一个序列化失败或者莫名其妙的响应。**"没 await" 是异步代码里最高频的 bug。**

### 8.2 在 `def` 里用 `await`

```python
def x():
    await something()          # ❌ SyntaxError
```

`await` 只能出现在 `async def` 里面。

### 8.3 `asyncio.sleep` 和 `time.sleep` 搞混

**名字只差几个字符，行为天差地别。**

- `asyncio.sleep(3)` → 让出控制权，别人能干活
- `time.sleep(3)` → 线程真的睡着

**写异步代码时，看到 `time.` 就要警觉。**

### 8.4 以为"异步 = 更快"

**异步不会让单个请求变快。** 一个 LLM 请求该等 5 秒还是 5 秒。

异步改变的是**同一时间能处理多少个**。

## 十、总结

这一课的核心只有一句：

> **"等别人"的时候，CPU 是闲着的。异步就是把这段空闲利用起来。**

拆成几层：

| 层面 | 结论 |
|---|---|
| **概念** | 异步 ≠ 更快，异步 = **同一时间能处理更多** |
| **FastAPI** | `def` 走线程池（有上限 40）；`async def` 走单线程事件循环 |
| **红线** | **`async def` 里绝不能有阻塞调用**，否则整店停摆 |
| **选择** | 只有"在等 I/O"才用异步；算东西、读 SQLite 都不需要 |

还有一条更通用的判断，比记住语法有用：

> **先问"我大部分时间在等谁"。**
> 等网络 → 异步。等磁盘 → 同步多线程。等 CPU 算完 → 都不是，该优化算法。

这条判断在你以后遇到"服务变慢了"的时候，第一步就能用上：**先分清是"等"还是"算"**。

**1.** 大致是：

```
/slow-sync   50 个并发请求  耗时 6.0 秒
/slow-async  50 个并发请求  耗时 3.0 秒
/slow-block   5 个并发请求  耗时 15.0 秒
```

具体数字会有波动，但**比例关系**（6 : 3 : 15）是关键。

**2.** 因为 `def` 接口跑在 **40 个线程**的线程池里：

- 前 40 个请求同时进入，各睡 3 秒 → 第 3 秒完成
- 剩下 10 个排队，等线程空出来 → 再睡 3 秒 → 第 6 秒完成

**40 是瓶颈**。改成 `40 个请求` 就是 3 秒，`41 个请求` 就是 6 秒。

**3.** **150 秒**（50 × 3）。

因为 `async def` 跑在**唯一的事件循环线程**上，而 `time.sleep` 会让这个线程真的睡死。一个请求睡的时候，后面的**一个都进不来**。

对比 `/slow-async`：`asyncio.sleep` 是"标记我在等，先把控制权交出去"，所以 50 个能同时处在等待状态。

**4.** **不该。**

`sqlite3` 是同步阻塞库——文件读写会阻塞线程。放进 `async def` 里，**每次查库都会冻住整个服务**，比现在还糟糕。

要真正做到异步数据库，得换异步驱动（如 `aiosqlite` / `asyncpg`），那是另一个成本。**课程项目不值得。**

**正确做法**：保持 `def` + `sqlite3`；需要调大模型的地方，单独用 `async def` + 异步 HTTP 客户端。

**5.** 三种写法，推荐**第二种**：

```python
# ① 全同步：简单，但调大模型时会占住一个线程 5 秒
@app.get("/x")
def x():
    ...
    res = httpx.get(...)       # 同步 HTTP
```

```python
# ② async def + 把 sqlite 的活扔进线程池（推荐）
import anyio

@app.get("/x")
async def x():
    res = await httpx_client.post(...)          # 异步调用
    rows = await anyio.to_thread.run_sync(read_from_sqlite)  # 阻塞活扔出去
```

```python
# ③ 全 def + 线程池：最省事
@app.get("/x")
def x():
    res = httpx.get(...)
```

关键在于：**不要让阻塞操作出现在事件循环线程里**。要么整个接口用 `def`（靠线程池兜底），要么 `async def` 里把阻塞部分显式扔进 `run_sync`。

> 课程项目推荐先走 ③——**简单、不容易错**。等真正遇到性能问题再优化，这是工程上正确的顺序。

**6.** 区别不在"总时长"，在**等待期间线程能不能干别的**：

| | `asyncio.sleep(5)` | `time.sleep(5)` |
|---|---|---|
| 谁在睡 | 这个**任务**被挂起 | 这个**线程**真的睡 |
| 别人能干活吗 | ✅ 事件循环去跑别的任务 | ❌ 线程被占死 |
| 需要 `async` 环境吗 | 需要 | 不需要 |
| 用途 | 异步代码里模拟等待 | 同步代码里模拟等待 |

**7.** 两个问题：

**① 在 `async def` 里用了阻塞的 `sqlite3`。**

`cur.execute` 和 `fetchall` 都是文件 IO，会卡住事件循环。请求一多，整个服务就会像 `/slow-block` 那样停摆。

**② 用了一个全局的 `conn`。**

第 7 课讲过：SQLite 连接**不能跨线程使用**。而这个接口既可能在事件循环线程上跑，也可能被别处用——迟早报 `SQLite objects created in a thread can only be used in that same thread`。

**改法**：要么整个接口改回 `def`（配第 10 课的 `Depends` 拿连接），要么 `async def` 里把数据库操作 `await anyio.to_thread.run_sync(...)` 扔出去，并用每次新建的连接。
